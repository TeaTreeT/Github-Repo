CVE-2026-30006 is a stack-based buffer overrun (buffer overflow) vulnerability in XnSoft NConvert version 7.230. It is triggered by processing a specially crafted TIFF (.tiff) file.
Severity and Impact

Affected Product: XnSoft NConvert 7.230 (a command-line image conversion tool).
Vulnerability Type: Stack Buffer Overrun (often classified under CWE-121: Stack-based Buffer Overflow).
Impact: Primarily Denial of Service (DoS) via crash (stack corruption leading to security check failure /GS exception). It is considered exploitable and could potentially allow arbitrary code execution in some scenarios, depending on the application's memory layout, protections (e.g., stack canaries/GS), and whether the overflow can be precisely controlled.
Attack Vector: Local or remote if the application processes untrusted TIFF files (e.g., via user upload, email attachment, or automated batch processing).
CVSS: Details on NVD indicate it uses CVSS v3.x / v4.0 scoring (exact base score not highlighted in summaries, but typical for such issues in image parsers is Medium to High).

How It Works
NConvert uses custom or library-based code to parse various image formats, including TIFF. TIFF files contain complex structures: headers, Image File Directories (IFDs), tags, and strips/tile data with variable lengths and offsets.
The vulnerability likely occurs in a TIFF parsing routine (e.g., when handling a specific tag, strip, or metadata field) where:

The code allocates a fixed-size buffer on the stack (e.g., char buf[256]; or similar).
It reads a length or data size from the malformed TIFF file without proper validation (e.g., no check against buffer size, integer overflow in size calculation, or trusting a malicious count field in a TIFF tag).
It then performs a copy operation (e.g., memcpy, strcpy, loop with buf[i] = data[i]) that exceeds the stack buffer bounds.

This overwrites adjacent stack memory, including:

Other local variables.
Saved frame pointer (EBP).
Return address.
Stack canary (if /GS is enabled).

In the provided PoC/debug output, triggering it with a crafted file via nconvert.exe -out tiff <malicious.tiff> results in a Security check failure or stack buffer overrun (code c0000409), confirming the classic /GS-protected stack overflow.
Attackers craft the TIFF by manipulating fields like tag values, strip byte counts, or compressed data to cause excessive copying.
Secure Code Fix / Mitigation Strategies
1. Immediate User Mitigation

Update to a patched version of NConvert (check the official site: xnview.com).
Avoid processing untrusted TIFF files. Sandbox the application or run with minimal privileges.
Use file format validation tools or libraries before feeding images to NConvert.

2. Developer Fixes (for similar image parsing code)
If you're maintaining similar C/C++ image processing code:
Bad Pattern (Vulnerable):

    char buffer[512];  // Fixed stack buffer

}

    // ... safely read reported_size with bounds checking on data_len ...

Key Best Practices:

Always validate input lengths against buffer capacity and file remaining bytes.
Use safe functions: strncpy, snprintf, or bounded memcpy equivalents.
Enable compiler protections: /GS (Visual Studio), -fstack-protector (GCC/Clang), ASLR, DEP/NX.
Adopt modern languages or safe libraries: Use libtiff (with latest patches) instead of custom parsers where possible. Consider Rust or memory-safe alternatives for new code.
Fuzz testing: Use AFL++, libFuzzer, or honggfuzz on your TIFF parser with crafted inputs.
Sandboxing: Run image converters in a sandbox (e.g., seccomp, AppContainer, or containers).
Bounds checking everywhere: Especially for multi-byte fields, offsets, and compressed data in formats like TIFF.
Error handling: Gracefully reject malformed files instead of crashing.

For library users, keep dependencies like libtiff, ImageMagick, or libpng up to date, as similar historical bugs (e.g., in older TIFF libraries) have led to many CVEs.
